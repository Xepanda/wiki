# 旁路由透明代理（OpenClash / PassWall）深度配置与全屋多终端接入指南

泰山派 OpenWrt 旁路由部署完成后，核心目标是实现**全屋网络无感透明代理**：
* 局域网各终端（手机、电脑、电视盒子、智能家居）**无需在本地安装任何代理客户端软件**；
* 设备只需将网络网关指向泰山派 `192.168.31.2`，即可实现国内流量极速直连、海外流量自动经加密节点智能分流；
* 支持最新现代协议（**Hysteria 2**、**VLESS Reality**、**Shadowsocks**）。

本篇完整记录从核心选型、Mihomo 内核升级、三大典型故障排错复盘、REST API 自动化控制，到多终端接入的实战经验。

## 2. OpenClash 适配与 Clash.Meta (Mihomo) 核心部署

现代机场节点普遍采用了 **Hysteria 2 (HY2)** 和 **VLESS Reality (XTLS-rprx-vision)** 协议。OpenWrt 原装旧版核心（如 Xray 1.5.x 或原版 Clash）无法解析此类新型节点，必须部署 **Clash.Meta（现称 Mihomo）** 核心。

### 2.1 获取并部署 ARM64 架构 Mihomo 内核
泰山派主控为瑞芯微 RK3566，指令架构为 `aarch64` (`linux/arm64`)：

```bash
# 1. 登录泰山派终端，下载最新的 Mihomo arm64 二进制发布包
curl -s -L "https://github.com/MetaCubeX/mihomo/releases/download/v1.19.30/mihomo-linux-arm64-v1.19.30.gz" -o /tmp/mihomo.gz

# 2. 解压并赋予可执行权限
gzip -dc /tmp/mihomo.gz > /tmp/clash_meta
chmod 755 /tmp/clash_meta

# 3. 部署至 OpenWrt 容器对应的 OpenClash 核心目录
docker cp /tmp/clash_meta openwrt:/etc/openclash/core/clash_meta
docker cp /tmp/clash_meta openwrt:/etc/openclash/core/clash
docker exec openwrt chmod 755 /etc/openclash/core/clash /etc/openclash/core/clash_meta

# 4. 验证内核架构与版本
docker exec openwrt /etc/openclash/core/clash_meta -v
# 输出: Mihomo Meta v1.19.x linux arm64 ...
```

## 3. 实战排障与三大深坑复盘（避坑宝典）

在部署与调优过程中，以下三个问题极其隐蔽，属于典型排错难点：

### 坑 1：Mihomo v1.18+ 路径安全校验报错 (`path is not subpath of home directory`)
* **报错现象**：启动 OpenClash 时核心秒退，日志提示：
  ```text
  level=fatal msg="Parse config error: path is not subpath of home directory or SAFE_PATHS: /usr/share/openclash/ui \n allowed paths: [/etc/openclash]"
  ```
* **根本原因**：新版 Mihomo 加强了安全沙箱，默认禁止将配置目录之外的 `/usr/share/openclash/ui` 作为外部控制面板路径；且 OpenClash 采用 `capsh --user=nobody` 降权启动核心，`capsh` 默认会丢弃父进程的大部分非白名单环境变量。
* **解决方案**：在 `/etc/init.d/openclash` 执行核心启动命令的 `nohup` 前显式注入环境变量：
  ```bash
  # 将 nohup $CLASH 替换为：
  nohup env SKIP_SAFE_PATH_CHECK=1 $CLASH -d $CLASH_CONFIG -f "$CONFIG_FILE" >> $LOG_FILE 2>&1 &
  ```

### 坑 2：OpenClash 内部探活误判 (`pidof clash`)
* **报错现象**：核心成功运行，但 OpenClash 在 `Step 5: Check The Core Status` 后立即报错退出。
* **根本原因**：OpenClash 的状态检查脚本固定使用 `pidof clash` 命令检索进程名。如果通过 shell 包装脚本启动或者重命名二进制为 `clash_meta_bin`，进程表中的进程名与 `clash` 不匹配，脚本误判内核崩溃从而强制停止服务。
* **解决方案**：内核物理二进制文件必须保持命名为 `clash` 或 `clash_meta`，避免通过多层 bash wrapper 调用。

### 坑 3：机场订阅自带 Basic 密码导致局域网 407 报错
* **报错现象**：终端设置代理后，浏览器弹窗要求输入用户名密码，命令行请求返回 `HTTP/1.1 407 Proxy Authentication Required`。
* **根本原因**：部分机场导出的 Clash YAML 配置中注入了 `authentication:` 字段（如随机生成的用户凭据）；同时 OpenClash 的 UCI 配置中可能残留了 `@authentication[0]` 节。
* **解决方案**：
  ```bash
  # 1. 删除 OpenWrt 内部生成的认证节
  docker exec openwrt uci delete 'openclash.@authentication[0]' 2>/dev/null || true
  docker exec openwrt uci commit openclash

  # 2. 剥离订阅 YAML 中的 authentication 配置块
  docker exec openwrt sed -i '/authentication:/,+1d' /etc/openclash/config/your_config.yaml
  ```

## 4. 自动化节点调度（Clash REST API）

OpenClash 启动后会开放外部控制端口（默认 `9090`，密钥通常为 `123456` 或后台设置的密码），支持通过 RESTful API 进行无感热切换与延迟测试：

```bash
# 1. 查询所有代理策略组当前选中的节点
curl -s -H "Authorization: Bearer YOUR_SECRET" http://192.168.31.2:9090/proxies | \
  python3 -c "import sys, json; d=json.load(sys.stdin)['proxies']; print({k: v.get('now') for k,v in d.items() if v.get('type')=='Selector'})"

# 2. 对特定节点发起延迟测试 (毫秒)
curl -s -H "Authorization: Bearer YOUR_SECRET" \
  "http://192.168.31.2:9090/proxies/YOUR_NODE_NAME/delay?timeout=5000&url=http://www.gstatic.com/generate_204"

# 3. 热切换目标组至指定节点 (如印度 BGP 节点，返回 204 即切换成功)
curl -X PUT -H "Authorization: Bearer YOUR_SECRET" -H "Content-Type: application/json" \
  -d '{"name": "🇮🇳 印度A[BGP]"}' \
  "http://192.168.31.2:9090/proxies/%F0%9F%94%B0%20%E8%8A%82%E7%82%B9%E9%80%89%E6%8B%A9"
```

## 5. 全屋终端接入旁路由配置指南

当旁路由运行平稳后，局域网终端可通过以下两种方式接入：

### 方式 A：修改设备网络参数（最推荐 ⭐⭐⭐⭐⭐，全自动无感）

这种方式最为优雅，终端**无需运行任何软件**，微信/国内网站走主路由直连，Google/GitHub/国外服务自动走旁路由加速。

| 操作系统 | 配置路径 | 关键参数设置 |
| :--- | :--- | :--- |
| **Windows 10 / 11** | 设置 ➔ 网络和 Internet ➔ Wi-Fi/以太网属性 ➔ IP 分配【编辑】(手动) | **IPv4 地址**：`192.168.31.188`<br/>**子网掩码**：`255.255.255.0` (或前缀 24)<br/>**默认网关**：**`192.168.31.2`**<br/>**首选 DNS**：**`192.168.31.2`** |
| **macOS (苹果电脑)** | 系统设置 ➔ 网络 ➔ Wi-Fi【详细信息】➔ TCP/IP (手动) ➔ DNS | **路由器 (Router)**：**`192.168.31.2`**<br/>**DNS 服务器**：**`192.168.31.2`** |
| **iOS (iPhone/iPad)** | 设置 ➔ 无线局域网 ➔ 点击当前 Wi-Fi ℹ️ ➔ 配置 IP (手动) ➔ 配置 DNS | **路由器**：**`192.168.31.2`**<br/>**DNS 服务器**：**`192.168.31.2`** |
| **Android (安卓手机)** | 设置 ➔ WLAN ➔ 长按或详情 ➔ IP 设置改为静态 | **网关**：**`192.168.31.2`**<br/>**域名 1**：**`192.168.31.2`** |

> **提示**：终端完成配置后，在浏览器访问 [https://ipinfo.io](https://ipinfo.io)，即可看到出口 IP 已变为所选节点的公网 IP。

### 方式 B：系统代理端口模式（免改网卡 IP，针对单机临时使用）

若不想更改设备网卡设置，也可以只让浏览器走泰山派开放的代理端口：
* **代理服务器 IP**：`192.168.31.2`
* **HTTP / Mixed 代理端口**：`7890`（或 `7893`）
* **SOCKS5 代理端口**：`7891`
* **适用场景**：公司电脑受组策略限制无法修改静态 IP、或者仅需特定浏览器走代理。

### 5.3 国内外智能分流验证与避坑（国内访问受影响吗？）

旁路由接入后，最常关心的核心问题是：“**使用旁路由后，国内网络访问、网银与微信会不会卡顿或被风控？**”

答案是：**完全不会。**

#### 1. 分流工作原理
* **规则分流机制 (Rule 模式)**：OpenClash 默认配置了庞大的国内主流域名规则集（包含微信、百度、淘宝、B站、各家网银等）直接命中 `🎯 全球直连` (DIRECT)；
* **GeoIP CN 兜底**：即便遇到白名单外的冷门国内网站，底部的 `GEOIP, CN ➡️ 🎯 全球直连` 会精准识别目标服务器位于中国大陆并直连；
* **零绕路不耗节点流量**：直连流量在软路由由 Linux 内核直接转交物理主路由（`192.168.31.1`）发送，跑满本地宽带物理千兆，延迟与不挂旁路由完全相同；
* **本地原生 IP 保障**：国内服务器识别到的依然是本地宽带原生公网 IP，不触发异地登录保护或风控。

#### 2. 双重验证命令（实测校验）
终端无论是配置透明网关还是配置端口代理，均可通过以下两条命令快速校验分流是否正常：

```bash
# 1. 验证国内流量是否保持本地原生宽带 IP (应返回本地真实运营商 IP，如浙江移动)
curl -s http://cip.cc
# 输出: IP: 183.247.23.xxx | 地址: 中国 浙江 杭州 移动

# 2. 验证海外流量是否走代理节点出口 (应返回所选节点 IP，如新加坡 / 香港)
curl -s http://ip-api.com/json
# 输出: "country":"Singapore", "isp":"Bage Cloud LLC", "query":"77.93.89.xxx"

# 3. 验证海外连通性与响应握手延迟
curl -s -o /dev/null -w "HTTP状态: %{http_code} | 总耗时: %{time_total}s\n" https://www.google.com
# 输出: HTTP状态: 200 | 总耗时: 0.25s
```

#### 3. 避坑要点
* **切忌误切 `Global (全局)` 模式**：平时必须保持在 **`Rule (规则)`** 模式，切成全局模式会导致所有国内流量强行绕道海外节点导致国内变慢；
* **极少部分私有服务**：若遇到极个别公司内网、学校 VPN 或老旧政务系统打不开，通常是 Fake-IP 机制所致，在 OpenClash 面板的 **“Fake-IP 本地绕过列表”** 添加对应域名即可。

## 6. 运维与运行指标总结

在实际接入多台电脑与手机并运行 4K 视频流媒体压测时：
* **泰山派系统负载**：四核平均负载在 `0.20 ~ 0.35` 之间，CPU 占用率极低；
* **内存占用**：OpenClash + Mihomo 内核常驻内存约为 **100MB ~ 140MB**，泰山派 2GB 内存充裕（可用 900MB+）；
* **芯片发热**：SoC 核心温度保持在 **47°C ~ 49°C**，被动散热片工作状态极佳。
